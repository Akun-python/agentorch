# Python 智能体编排底层框架 v1 设计方案

## Summary

目标是设计一个**代码优先、异步优先、可直接作为 Python 库调用**的智能体编排框架，首版优先支持 `openai` 官方 Python SDK，并围绕你指定的 11 个模块外加 `沙盒管理层` 建立一套简洁、稳定、可扩展的底层架构。

首版定位明确为：

- 一个可安装、可导入、可编程调用的 Python 库
- 默认支持 OpenAI-compatible 模型接入
- 支持工具调用、skill 资源包、记忆、workflow 编排、推理控制
- 调用方式简单，用户能快速跑通单 agent 和多步任务
- 模块边界清晰，后续可以替换模型、存储、沙盒、日志、策略实现

推荐库名：

- 包名：`agent_orchestrator`
- 项目名：`agent-orchestrator`

推荐首版总目录：

```text
agent_orchestrator/
├── core/
├── models/
├── tools/
├── skills/
├── memory/
├── workflow/
├── runtime/
├── reasoning/
├── prompts/
├── parsing/
├── observability/
├── sandbox/
├── config/
├── plugins/
└── __init__.py
```

## Key Changes

### 1. 模型接入层 `models`

职责是统一不同模型提供方的调用方式，首版只落地 OpenAI-compatible provider，但接口必须通用。

核心对象：

- `BaseModel`
- `ModelRequest`
- `ModelResponse`
- `StreamChunk`
- `UsageInfo`
- `OpenAIModel`

v1 必须支持：

- chat completion
- 流式输出
- tool calling
- 结构化输出
- timeout / retry
- `api_key` / `base_url` / `model` / `max_tokens` 等统一配置

设计原则：

- 上层只依赖统一模型接口，不直接依赖 OpenAI SDK 原始返回结构
- 所有 provider 输出统一归一化为 `ModelResponse`
- token usage、finish_reason、tool_calls 一律标准化

用户调用示例：

```python
model = OpenAIModel(
    model="gpt-4.1",
    api_key="...",
    base_url=None,
)
response = await model.generate(request)
```

### 2. 工具调用模块 `tools`

职责是定义、注册、校验、执行工具，作为 agent 与外部能力交互的统一边界。

核心对象：

- `BaseTool`
- `ToolSpec`
- `ToolResult`
- `ToolError`
- `tool` 装饰器
- `ToolRegistry`

v1 设计要求：

- 工具输入必须结构化，推荐基于 `pydantic`
- 工具输出必须结构化，不允许只返回字符串状态
- 工具是原子动作，不承载复杂流程
- 工具元信息至少包含：
  - `name`
  - `description`
  - `input_schema`
  - `risk_level`
  - `timeout`
  - `retryable`

执行策略由 runtime 统一负责，不单独做重型 executor 子系统。  
工具层只保证“定义清楚、元信息完整、可被统一执行”。

### 3. Skill 系统模块 `skills`

职责是组织任务级能力包，而不是执行引擎本身。

核心对象：

- `Skill`
- `SkillManifest`
- `SkillLoader`
- `SkillRegistry`

Skill 目录规范固定为：

```text
my-skill/
├── SKILL.md
├── references/
├── scripts/
└── assets/
```

Skill 包含的能力：

- 定义何时触发
- 说明任务处理流程
- 约束工具使用边界
- 提供 prompt 片段与参考资源
- 暴露脚本资源位置

设计原则：

- `SKILL.md` frontmatter 只放最小元信息
- 正文放核心说明
- 详细规则放 `references/`
- 重复性强的辅助逻辑放 `scripts/`
- Skill 不直接执行脚本，执行仍由 runtime 或工具层调度

### 4. 记忆系统模块 `memory`

职责是管理运行态、短期记忆、长期记忆和恢复快照，但对外 API 保持简洁。

核心对象：

- `MemoryManager`
- `StateStore`
- `CheckpointStore`
- `RecordStore`
- `MemoryRecord`

概念划分固定为四层：

- `state`：当前 run 的运行上下文
- `thread memory`：同一 thread 下的消息与短期摘要
- `long-term memory`：跨 thread 的高价值信息
- `checkpoint`：恢复执行的快照

v1 默认实现：

- `InMemoryStateStore`
- `SQLiteCheckpointStore`
- `SQLiteRecordStore`

职责固定：

- 加载 thread 相关上下文
- 控制消息窗口与摘要压缩
- 写入长期记忆
- 提供检索接口
- 支持断点恢复

不在 v1 强绑定向量数据库。长期记忆先以结构化记录 + 关键词/标签检索为主。

### 5. 任务编排 / Workflow 模块 `workflow`

职责是描述和执行多步任务流程。

核心对象：

- `Workflow`
- `Node`
- `Edge`
- `WorkflowRunner`

v1 支持 DAG，但保持节点种类精简。  
节点类型固定为：

- `model`
- `tool`
- `router`
- `memory`

边类型固定为：

- `success`
- `failure`
- `condition`

执行规则：

- workflow 从入口节点启动
- 节点接收 `Context`
- 节点执行后返回结构化结果
- router 决定下一跳
- workflow 控制最大步数、终止条件和错误传播

不在 v1 引入复杂 YAML DSL，workflow 采用 Python API 定义，降低实现复杂度并保持可控。

### 6. Agent Runtime 运行时模块 `runtime`

这是整个框架的核心编排层，负责把所有模块接起来。

核心对象：

- `Runtime`
- `Agent`
- `Context`
- `RunResult`

职责：

- 装配 model、tool registry、skill registry、memory manager、workflow、sandbox
- 管理一次 agent run 的生命周期
- 调用 reasoning policy 选择下一步动作
- 协调 prompt 构建、模型调用、工具执行、memory 更新、日志上报
- 返回标准化结果

统一入口 API 固定为：

```python
runtime = Runtime(
    model=model,
    tools=tool_registry,
    skills=skill_registry,
    memory=memory_manager,
    sandbox=sandbox_manager,
)
agent = Agent(runtime=runtime, workflow=workflow)
result = await agent.run("请帮我完成任务", thread_id="thread-001")
```

同步接口只提供薄包装：

```python
result = agent.run_sync(...)
```

### 7. 推理控制模块 `reasoning`

职责是定义 agent 如何思考和决策，不将调度逻辑写死在 prompt 中。

核心对象：

- `BasePolicy`
- `Decision`
- `ActionType`
- `ReactPolicy`

v1 先内置一种稳定策略：

- `ReactPolicy`

但架构必须允许后续扩展：

- `PlanExecutePolicy`
- `RouterPolicy`
- `MultiAgentPolicy`

`Decision` 结构统一限制为：

- `respond`
- `call_tool`
- `select_skill`
- `route`
- `finish`

这样 reasoning 模块既有扩展性，又不会首版过重。

### 8. Prompt 管理模块 `prompts`

职责是统一管理系统提示、skill 提示、工具提示、记忆提示和结构化输出提示。

核心对象：

- `PromptTemplate`
- `PromptBuilder`
- `PromptContext`

v1 只做最必要能力：

- 管理系统 prompt
- 注入 skill 指令
- 注入 memory 摘要
- 注入工具说明
- 注入输出格式约束
- 生成最终模型请求消息

模板实现保持简单：

- 首版使用 Python 模板字符串或 Jinja2
- 不做在线 prompt 平台
- 不做复杂版本中心

### 9. 结构化输出 / 解析模块 `parsing`

职责是把模型输出和工具参数转换成可验证的 Python 对象。

核心对象：

- `OutputParser`
- `PydanticParser`
- `ParseError`

v1 要求：

- tool 参数解析统一走 parser
- reasoning decision 统一走 parser
- workflow 节点结构化输出统一走 parser
- parser 失败允许一次自动纠错重试
- 失败后返回标准解析异常

核心原则：

- 所有关键边界都结构化
- 不让自由文本直接驱动调度逻辑

### 10. 观察性 / 日志 / 调试模块 `observability`

职责是记录 agent 运行链路、模型调用、工具调用、memory 读写和成本信息。

核心对象：

- `Logger`
- `Tracer`
- `EventBus`
- `UsageTracker`

统一上下文字段至少包括：

- `request_id`
- `run_id`
- `thread_id`
- `trace_id`

v1 记录的关键事件：

- `run_started`
- `prompt_built`
- `model_called`
- `tool_called`
- `memory_read`
- `memory_written`
- `workflow_step_completed`
- `run_completed`
- `run_failed`

v1 默认输出：

- 控制台结构化日志
- 本地文件日志
- token / cost usage 汇总

不要求首版接入 LangSmith 或 OpenTelemetry，但字段设计要兼容未来扩展。

### 11. 配置与插件模块 `config` / `plugins`

职责是统一框架配置和后续扩展点。

核心对象：

- `RuntimeConfig`
- `ModelConfig`
- `MemoryConfig`
- `SandboxConfig`
- `Plugin`
- `PluginManager`

配置原则：

- 首版以 Python 配置对象为主
- 环境变量作为补充
- 不做复杂 YAML 配置中心

插件扩展点固定为：

- model provider plugin
- tool plugin
- memory backend plugin
- policy plugin
- sandbox plugin

Skill 不走插件机制，继续走资源包加载系统。

### 12. 沙盒管理层 `sandbox`

这是新增模块，职责是为高风险工具和代码执行提供隔离边界。

核心对象：

- `SandboxManager`
- `SandboxSession`
- `SandboxPolicy`
- `ExecutionResult`

v1 主要支持的沙盒能力：

- shell 命令执行封装
- Python 代码执行封装
- 文件访问范围控制
- 超时控制
- 资源限制接口预留
- 命令白名单 / 黑名单接口预留

设计原则：

- 沙盒是工具执行环境，不是工具本身
- 高风险工具必须通过 sandbox 执行
- runtime 在调用工具时根据工具元信息决定是否进入 sandbox
- sandbox 结果统一结构化返回，包含 stdout、stderr、exit_code、duration

v1 不强做容器级隔离，但接口必须允许未来替换为：

- subprocess sandbox
- Docker sandbox
- remote sandbox

推荐分层：

- `LocalSubprocessSandbox` 作为默认实现
- `SandboxPolicy` 控制路径、超时、可执行命令
- `SandboxManager` 负责 session 生命周期

## Public Interfaces

首版建议对外只暴露这组核心 API：

```python
from agent_orchestrator import (
    Agent,
    Runtime,
    Context,
    Workflow,
    OpenAIModel,
    tool,
    ToolRegistry,
    SkillLoader,
    SkillRegistry,
    MemoryManager,
    SandboxManager,
)
```

用户最小使用路径固定为三步：

1. 定义 model、tools、skills、memory、sandbox
2. 组装 runtime
3. 创建 agent 并调用 `run()` 或 `run_sync()`

## Test Plan

必须覆盖以下测试场景：

- OpenAI model 普通调用、流式输出、tool calling、结构化响应
- tool 注册、schema 校验、超时、异常包装
- skill 目录加载、frontmatter 解析、references/scripts/assets 解析
- memory 的 thread 隔离、checkpoint 保存与恢复、长期记录读写
- workflow 顺序执行、条件路由、失败传播、最大步数保护
- runtime 能串起 model、tool、skill、memory、workflow
- reasoning policy 能输出结构化决策并驱动工具调用
- prompt builder 能正确注入 skill、memory、tool 信息
- parser 解析失败后的自动纠错与异常上抛
- observability 能完整记录 run 链路和 usage
- sandbox 执行 shell/python 任务时能正确应用超时和路径约束
- 高风险工具走 sandbox，低风险工具可直连执行

端到端 demo 至少包含：

- 单轮问答 agent
- 工具调用 agent
- skill + memory + workflow agent
- sandbox 工具执行 agent

## Assumptions

- 首版只优先支持 OpenAI-compatible 模型调用
- 首版长期记忆不接向量数据库，先用结构化存储方案
- 首版 workflow 用 Python API 定义，不做 YAML DSL
- 首版默认本地可运行，不承诺分布式部署能力
- 首版沙盒默认采用本地 subprocess 模式，不强制容器化
- 首版默认 Python 版本为 `3.11+`
- 首版核心依赖建议控制在：`openai`, `pydantic`, `httpx`, `sqlalchemy`, `jinja2`
- 首版设计重点是“简洁 + 可扩展”，因此保留稳定接口和替换点，但不一次性实现全部高级能力
